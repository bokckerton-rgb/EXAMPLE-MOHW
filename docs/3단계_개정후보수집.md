# 3단계 · 개정 후보 수집 (law-history-sync) 실행 순서

이번 범위: **버전 목록 → 두 버전 비교(신설·개정·삭제 조문 + 관련 부칙) → 후보 저장(중복 없이)**
다음(4단계): 저장된 후보를 OpenRouter로 평가해 최대 10건 확정 → 홈페이지·HWPX 공용

| 파일 | 넣는 곳 |
|---|---|
| `supabase/02_law_revision_candidates.sql` | Supabase **SQL Editor** |
| `supabase/functions/law-history-sync/index.ts` | Supabase **Edge Functions → Via Editor** |

기존 법령 조회 함수와 `task_laws`, `LAW_OC` Secret은 **그대로** 씁니다. 새 Secret 등록은 필요 없어요.
> 참고: Example project에서 기존 함수 이름은 `law-fulltext`이고 Secret 이름은 `LAW_OC`입니다. 다른 프로젝트에서 Secret 이름을 바꿨다면 코드의 `env('LAW_OC')` 한 곳만 맞춰 주세요.

---

## 1단계 · SQL 넣기
1. **SQL Editor → New query** → `supabase/02_law_revision_candidates.sql` 전체 붙여 넣기 → **Run**
2. 결과에 `candidate_rows = 0` 이 보이면 성공 (다시 Run 해도 안전)

## 2단계 · 함수 배포 (Via Editor)
1. **Edge Functions → Deploy a new function → Via Editor**
2. 이름: `law-history-sync`
3. 기본 코드를 지우고 `index.ts` 전체 붙여 넣기 → **Deploy function**
4. 함수 화면 **Details** 탭 → **Verify JWT with legacy secret** 끄기 → 저장
   - 대신 코드가 직접 "서버용 키로 불렀는지" 검사합니다. 공개 키(publishable/anon)로 부르면 401로 거절돼요.

## 3단계 · Test 창에서 첫 실행
함수 화면 오른쪽 위 **Test** 버튼 →

| 칸 | 넣을 값 |
|---|---|
| HTTP Method | `POST` |
| Authorization / Role | **service_role** 선택. 선택 칸이 없으면 Headers에 `Authorization` = `Bearer <service_role 키>` 추가 (Project Settings → API Keys → **Legacy API Keys** 탭의 service_role) |
| Headers | `Content-Type: application/json` |
| Request Body | 아래 JSON |

```json
{ "task_id": "child-allowance" }
```
→ **Send Request**

> 키는 Test 창에서만 쓰고, 코드·HTML·GitHub·캡처 화면에는 남기지 마세요. 법제처 OC는 서버 Secret에서만 읽기 때문에 입력값·응답 어디에도 나오지 않습니다.

## 4단계 · 중복 저장 안 되는지 확인
1. Test 창에서 **같은 입력값으로 한 번 더** Send
   - 기대값: `save_result: "unchanged"`, `saved: { inserted: 0, updated: 0, unchanged: 1 }`
2. SQL Editor에서 확인:
```sql
select candidate_key, promulgation_date, to_ef_yd, revision_type,
       added_count, modified_count, deleted_count,
       first_seen_at, last_synced_at
from public.law_revision_candidates
where task_id = 'child-allowance';
```
   - 기대값: **1줄**. `first_seen_at`은 첫 실행 시각 그대로, `last_synced_at`만 두 번째 실행 시각으로 바뀜

## (선택) 연혁 전체 후보 모으기
4단계 평가용으로 과거 개정까지 모을 때:
```json
{ "task_id": "child-allowance", "max_pairs": 12 }
```
- 시행된 버전 9개 → 후보 최대 8건 (이미 있던 1건은 `unchanged`, 나머지 `inserted`)
- 저장 없이 미리보기: `"dry_run": true` / 시행예정본까지 포함: `"include_future": true`
- 같은 공포번호가 시행일만 나뉜 경우(예: 법률 제21489호 2026.3.20 / 3.27 분리시행)도 각각 후보가 됩니다. 바뀐 조문이 0건인 후보는 4단계에서 걸러 쓰면 돼요.

## 응답 구조 (4단계·HWPX에서 그대로 사용)
```
candidates[]
  candidate_key, law_id, law_name
  from_mst, from_ef_yd → to_mst, to_ef_yd      (비교한 두 버전)
  promulgation_date, promulgation_no, revision_type, is_future
  source_url, previous_source_url             (개정 후 / 개정 전 원문)
  added_count, modified_count, deleted_count
  changed_articles[]  article, title, change_type(added|modified|deleted), change_label(신설|개정|삭제),
                      before_text, after_text, removed_lines[], added_lines[]
  supplementary_provisions[]  title, promulgation_no, promulgation_date, text
  save_result  inserted | updated | unchanged | dry_run
```
DB 표 `law_revision_candidates`에는 같은 내용 + `status`(지금은 `collected`) + `first_seen_at` / `last_synced_at`이 저장됩니다.

## 오류 문구별 조치
| 응답 | 조치 |
|---|---|
| 401 `NEED_SERVER_KEY` | Test 창 Authorization을 service_role로 |
| 400 `BAD_TASK_ID` | Body가 `{ "task_id": "child-allowance" }` 인지 |
| 404 `NO_LINK` | task_laws에 해당 업무가 있는지 |
| 500 `NO_OC` | Edge Functions → Secrets에 `LAW_OC` |
| 500 `DB_ERROR` 저장용 표가 없어요 | 1단계 SQL 실행 |
| 502 `LAW_NOT_JSON` | open.law.go.kr에서 OC 값, **시행일 법령 목록·본문** API 신청 여부 확인 |
| 502 `NO_VERSIONS` | `hint.item_fields_seen`·`other_law_ids_in_result`를 개발 담당에게 전달 (법령명 검색 결과에 013103이 없다는 뜻) |
